# 7.2 upgrade technical debt

> **Status (2026-09-04): active.**
>
> This is a living record of technical debt accepted while rebasing the
> VFMIG work onto 7.2. Each item describes the current compromise, the target
> state, and the evidence required before it can be closed.

## 1. Make `mlx5_dma_pool` VFMIG-aware

* **Status:** Open
* **Area:** mlx5 fragmented DMA-buffer allocation
* **Estimated effort:** 3-5 engineering days for implementation and validation

### Context

The 7.2 base routes fragmented mlx5 buffers through the
[fragment-buffer allocator][alloc],
using `mlx5_dma_pool`. Pools are organized by NUMA node and block size. A pool
allocates a `PAGE_SIZE` coherent backing page and suballocates fragments from
it with a bitmap.

VFMIG instead requires selected buffers to have deterministic IOVAs in
resource-specific slots defined by the
[VFMIG IOVA-slot contract][iova-slots].
A tracked VF must allocate these buffers through `vfmig_iova_alloc_slot()` so
that source and destination recreate the same device-visible addresses.

### Debt accepted during the upgrade

The rebase preserved the new pool for PFs and untracked VFs, but slot-routed
allocations on tracked VFs bypass it and allocate each fragment directly from
the VFMIG slot allocator. This currently covers:

* EQ buffers in `VFMIG_SLOT_EQ_BUF`;
* work-queue fragmented buffers in `VFMIG_SLOT_FRAG_BUF`; and
* other users of the exported fragment-buffer allocator through the
  `VFMIG_SLOT_DMA_COHERENT` catch-all.

The bypass was necessary because an ordinary shared pool page can contain
blocks belonging to unrelated consumers. Registering that page in one VFMIG
slot would collapse those consumers into the same allocation sequence and
undermine the slot isolation used for deterministic restore.

As a result, tracked VFs have a separate allocation and free path, do not get
sub-page packing from the pool, and require VFMIG-specific state on
`struct mlx5_frag_buf` to select the matching free path.

On a 4 KiB-page kernel, the minimum pool block is also 4 KiB, so a backing page
contains only one block and the bypass has little practical memory cost. The
lost packing becomes relevant on kernels with a larger `PAGE_SIZE`, such as
64 KiB.

### Catch-all conflict and external consumers

Rebasing the DMA-coherent catch-all from `5159dd111776` to
`028f2d1e20df` required a semantic conflict resolution. The original change
assumed that every fragment was allocated and freed directly. In the 7.2 base,
the exported `mlx5_frag_buf_alloc_node()` function had become the pool
allocator and `VFMIG_SLOT_INVALID` had become the ownership tag for a
pool-backed buffer.

The resolution retained the pooled implementation as the private
`mlx5_frag_buf_alloc_node_pool()` fallback, recreated the exported function as
a wrapper requesting `VFMIG_SLOT_DMA_COHERENT`, and preserved separate
direct-VFMIG and pool free paths. It correctly dropped the original conversion
of a zero-valued slot to `DMA_COHERENT`: zero now identifies a pooled buffer,
and converting it would free a pool sub-block through the wrong allocator.

The exported GPL interface is used outside `mlx5_core` by these audited
in-tree consumers:

* `mlx5_ib`: kernel-owned CQ buffers, including resize buffers, and kernel
  QP and SRQ buffers;
* `vfio-pci-mlx5`: migration page-tracker CQ and receive-QP buffers; and
* mlx5 vDPA: CQ, receive-QP, and driver-owned UMEM buffers.

This applies to their uses of `mlx5_frag_buf_alloc_node()`, not to every
coherent DMA allocation made by those drivers. An out-of-tree GPL module can
also call the exported helper and inherit the same behavior.

On a tracked VF, all such allocations bypass `mlx5_dma_pool` and share
`VFMIG_SLOT_DMA_COHERENT`. On a PF or untracked VF, the same API falls back
to the ordinary pool. This has several implications:

* Allocation layout and ownership now depend on whether the device is tracked,
  despite the unchanged function signature. Callers must preserve the
  allocator-populated fields and pair every allocation with
  `mlx5_frag_buf_free()`.
* The pool and VFMIG changes modified public mlx5 structure layouts, including
  `struct mlx5_buf_list` and `struct mlx5_frag_buf`. Separately built
  modules using these structures need a kernel-ABI review and rebuild.
* Tracked buffers are absent from pool debugfs accounting and create a VFMIG
  allocation, mapping, and registry entry for each fragment. On a 64 KiB-page
  kernel, the ordinary pool can pack sixteen 4 KiB blocks into one backing
  page, while the direct path can consume one registered page per fragment.
* The direct path forces `page_shift = PAGE_SHIFT`, while the pool can select
  a smaller block shift. This changes PAS entry layout and firmware
  `log_page_size` values on large-page kernels.
* The catch-all isolates these consumers from EQ and mlx5_core WQ ordering,
  but not from one another. A probe, feature, resize, create/destroy cycle, or
  future call site can shift every later IOVA in the catch-all slot. Replay
  therefore depends on the aggregate same-sizes, same-order history of
  whichever consumers are active on a VF.
* The catch-all slot is a fixed 510 MiB bump-allocated window. Free removes a
  mapping but does not rewind or reuse its cursor range, so repeated dynamic
  object churn can exhaust the slot based on cumulative allocations even when
  little memory remains live.
* Driver unwind and unbind must release every catch-all buffer before the
  VFMIG domain is cleared or destroyed. The free helper consults the device's
  current domain, so backend symmetry depends on that teardown ordering.
* A future exported-helper caller on a tracked VF silently joins the catch-all
  instead of failing on an unrouted coherent allocation. This improves
  compatibility but removes the fail-closed signal that the new resource
  needs a slot and restore-order review.

The rebased commit message still says that `mlx5_frag_buf_free()` converts a
zero-initialized slot to `DMA_COHERENT`; the resolved code deliberately does
not. The `struct mlx5_frag_buf::vfmig_slot` comment also describes `INVALID`
as the legacy coherent path, although it now selects pool ownership. Both
descriptions are stale.

### Desired state

Reuse the pool machinery for tracked VFs without sharing a backing page across
VFMIG slots:

* Partition tracked pool pages by VFMIG slot and block size. A physical
  backing page must belong to exactly one slot.
* Allocate and register the entire `PAGE_SIZE` backing page through
  `vfmig_iova_alloc_slot()`, then return fragments as offsets within it.
* Record the allocation backend and slot on the pool page, not on each
  fragment buffer.
* Unregister and free the whole backing page only after its final fragment is
  returned.
* Route EQ, work-queue, and catch-all fragmented-buffer allocations through
  the slot-aware pool while leaving PF and untracked-VF behavior unchanged.
* Preserve the exported allocation/free API so external-to-`mlx5_core`
  callers do not need to understand VFMIG slots or allocation backends.
* Decide whether `VFMIG_SLOT_DMA_COHERENT` provides a sufficient restore
  contract or must be split into stable subsystem or resource-specific slots.
* Define how repeated allocation churn remains within the finite slot window.
  Pooling alone does not recycle the VFMIG allocator's bump cursor.
* Require every new exported-helper call site to document its resource
  identity, allocation order, lifetime, and slot choice.
* Extend pool diagnostics so use can be inspected by slot as well as by block
  size and NUMA placement.

NUMA placement must not silently become part of the deterministic IOVA layout.
The logical tracked pool should be selected by slot and block size; a NUMA node
may be used as a backing-page placement hint. Otherwise, different source and
destination NUMA routing can change page packing and therefore fragment IOVAs.

### Constraints and open decisions

* The VFMIG allocator and registry use `PAGE_SIZE` as their allocation,
  registration, and free granule. Blocks from different VFMIG slots therefore
  cannot safely share one physical backing page without a substantially more
  complex aliasing and ownership design.
* The VFMIG IOVA domain must outlive every registered pool page. Allocation
  failure and device teardown must release a page through the same backend and
  slot that created it.
* Slot-separated pools preserve the current same-sizes, same-order allocation
  contract when source and destination start with empty pools. They do not make
  placement independent of allocation and free history.
* On kernels where `PAGE_SIZE` is greater than 4 KiB, pooling changes fragment
  packing and firmware-visible addresses relative to the direct allocation
  path. Migration compatibility between kernels on opposite sides of this
  change must either be excluded explicitly or handled through layout
  versioning or replay.

### Completion criteria

* No pool backing page serves more than one VFMIG slot.
* Tracked EQ, work-queue, and catch-all fragmented buffers allocate and free
  through the pool with symmetric whole-page VFMIG registration.
* PF and untracked-VF allocation behavior remains unchanged.
* Source and destination produce matching fragment IOVAs for the supported
  allocation contract, including when NUMA placement differs.
* Tracked allocations use the pool's normal `page_shift`, PAS entry count, and
  alignment rules on both 4 KiB and 64 KiB-page kernels. EQ/WQ
  `log_page_size` and PAS contents are validated on 64 KiB kernels.
* Tests cover 4 KiB and 64 KiB `PAGE_SIZE`, partial allocation failure, slot
  exhaustion, last-block page release, concurrent allocation, and device
  teardown.
* Replay tests cover a partially occupied backing page and matching
  create/free/reallocate histories before SAVE. Any history that cannot be
  replayed deterministically is documented as unsupported.
* Allocation-failure unwind and device unbind return VFMIG registry, mapping,
  and pool allocated-block counts to their baselines without unknown-IOVA,
  size-mismatch, or slot-mismatch warnings.
* The audited mlx5_ib, VFIO migration, and mlx5 vDPA buffers are covered by
  tracked and untracked create, resize where applicable, destroy/recreate,
  failure-unwind, driver-unbind, and SAVE/LOAD tests.
* Tests vary enabled consumers and object-creation order and either demonstrate
  deterministic catch-all placement or document and enforce the required
  source/destination ordering.
* Capacity tests exercise repeated create/free cycles beyond the live-memory
  high-water mark and either demonstrate bounded cursor use or document and
  enforce the exhaustion limit.
* SAVE/LOAD validation completes with active EQ and work-queue traffic.
* Pool debugfs accounting exposes or correctly aggregates tracked slot usage.

### Estimate

A focused, slot-partitioned implementation should take about 1-2 days and
roughly 100-250 lines, primarily in `drivers/net/ethernet/mellanox/mlx5/core/alloc.c`.
Failure-path, teardown, 4 KiB/64 KiB, and hardware migration validation should
take another 2-3 days.

History-independent placement or cross-version migration between the direct
and pooled layouts is a separate design problem and would likely take 1-3
weeks plus hardware validation.

The 3-5 day estimate assumes that the existing catch-all slot and
same-sizes, same-order contract remain supported. Splitting external consumers
into new slots, recycling cursor space, or adding keyed placement expands the
scope and requires a separate estimate.

## 2. Put fixed-handle UAR restore behind an upstreamable uverbs API

* **Status:** Open
* **Area:** RDMA uverbs object lifecycle and mlx5 dynamic-UAR restore
* **Estimated effort:** 2-5 days for a narrow core wrapper; 1-3 weeks for a
  declarative core/UAPI design and upstream validation

### Context

`MLX5_IB_METHOD_VFMIG_RESTORE_DYN_UARS` recreates each
`MLX5_IB_OBJECT_UAR` at the exact ufile handle and mmap offset captured on the
source. Those values are part of the provider-visible state retained by the
checkpointed process; allocating a different handle or mmap offset and hoping
to translate it later is not equivalent.

The normal uverbs attribute dispatcher owns allocation, commit, and abort for
an object declared with `UVERBS_ACCESS_NEW`. It does not provide a way to
request a specific IDR handle, supports only one new or destroyed object per
method, and rejects `UVERBS_ACCESS_NEW` and `UVERBS_ACCESS_DESTROY` on an
`UVERBS_ATTR_TYPE_IDRS_ARRAY`. The batched dynamic-UAR restore method therefore
cannot express its operation through the normal declarative interface.

The current [dynamic-UAR restore handler][dyn-uar-restore] works around that
limitation by driving the uverbs transaction directly for every record:

* `rdma_alloc_begin_uobject_at_handle()` reserves the source handle, takes the
  usual destruction exclusion, and charges the RDMA cgroup;
* `restore_uar_entry()` recreates the mlx5 mmap entry at the source pgoff;
* `rdma_alloc_commit_uobject()` publishes a successful object; and
* `rdma_alloc_abort_uobject()` unwinds a failed object before commit.

Only the three `rdma_alloc_*()` helpers require the `rdma_core` namespace.
`restore_uar_entry()` and its inline `rdma_user_mmap_entry_insert_exact()`
call do not.

### Debt exposed during the upgrade

The original `d82d5b724ad7` implementation already called these low-level
helpers. On its base, `rdma_core.o` was linked into `ib_uverbs.ko`, and the
VFMIG series exported the helpers as ordinary symbols. The cross-layer
dependency therefore existed but was implicit.

Upstream 7.2 commit `2274d8cb4912` moved driver-callable uverbs implementation
into `ib_uverbs_support.ko` so hardware drivers would not depend on the full
uverbs frontend. It also placed the lifecycle exports in the GPL-only
`rdma_core` symbol namespace. The rebased exact-handle helper in
`1a6fe7ff926a` follows that convention with `EXPORT_SYMBOL_NS_GPL`.

Consequently, `ad4b49a53e40` adds `MODULE_IMPORT_NS("rdma_core")` to
`mlx5_ib.ko`. The restore implementation itself is unchanged between the old
and rebased commits. The import is module metadata that acknowledges use of
the namespace; references to the exported helpers create the actual dependency
on `ib_uverbs_support.ko`.

This is an improvement over the old binary dependency, and the support module
was explicitly created for exceptional driver callers. It remains an
upstream-facing design concern:

* `mlx5_ib` is the only hardware driver in this tree importing `rdma_core`;
  the other importer is the `ib_uverbs` frontend itself.
* Driver code manually participates in uverbs IDR/XArray, reference, lock,
  RDMA-cgroup, and type-class lifecycle rules that the dispatcher normally
  encapsulates. It assigns `uobj->object` directly and relies on commit to
  consume the uobject reference and release `hw_destroy_rwsem`, or abort to
  erase the handle reservation and reverse the RDMA-cgroup charge.
* The namespace import applies to the whole `mlx5_ib` module. Once present,
  another use of a `rdma_core` export does not require a new import and is less
  visible during review.
* Placing the import in `main.c` makes it visible even when
  `CONFIG_INFINIBAND_USER_ACCESS=n` and `vfmig_uctx.o` is not linked. This is
  harmless because an unused import creates no provider dependency. Kbuild
  gates both `vfmig_uctx.o` and `ib_uverbs_support.ko` on user access, but the
  unused metadata obscures which code owns the exception. No missing Kconfig
  dependency is evident in the current arrangement.
* The batched restore commits records one at a time. A later-record failure
  leaves earlier UARs committed and requires the caller to close the ucontext
  before retrying. Any replacement API must define whether that behavior is
  preserved or made transactional.

The namespace was introduced partly to make exceptional consumption of this
interface visible. Removing the namespace declaration would hide the
dependency rather than resolve it.

### Remediation options

1. **Add fixed-handle `NEW` semantics to the uverbs dispatcher.** Extend the
   attribute machinery with a core-owned exact-handle allocation mode, such as
   `UVERBS_ACCESS_NEW_FIXED`. The dispatcher would reserve, commit, and abort;
   mlx5 would only validate the record and construct the UAR mmap object. This
   is the cleanest boundary. It requires either changing restore to one UAR per
   method or designing explicit array and partial-failure semantics.
2. **Move restore orchestration into a generic uverbs restore dispatcher.**
   Follow the model used for standard PD, MR, CQ, and QP restore: core owns the
   uobject lifecycle and invokes an mlx5 callback for the driver-private UAR.
   This could retain a batch interface, but it needs a generic extension point
   for vendor object types and a clear rollback contract.
3. **Export one narrow transaction helper from `ib_uverbs_support`.** A helper
   could reserve an exact handle, invoke a driver initializer, and then commit
   or abort internally. This retains the namespace and support-module
   dependency but stops mlx5 from open-coding the raw lifecycle triplet. The
   helper needs an explicit ownership contract for initializer failure and
   partially constructed driver state.
4. **Retain the current exception with explicit maintainer agreement.** Move
   `MODULE_IMPORT_NS` into `vfmig_uctx.c` for conditional ownership locality,
   or retain its conventional placement with the module metadata in `main.c`.
   Either location is cosmetic: document why exact handles require the escape
   hatch, and do not treat relocation as closing the debt.
5. **Allocate new handles and translate them in userspace.** CRIU and libmlx5
   could maintain an old-to-new handle and mmap-offset map. This avoids the
   kernel lifecycle dependency, but opaque provider handles may exist in
   application memory and shared state. The approach is invasive and is not a
   safe default without proving that every reference can be translated.

Do not resolve this by restoring ordinary exports, moving the helpers into
always-loaded `ib_core`, duplicating the uverbs object manager in mlx5, or
relying on normal IDR allocation order. Those choices either defeat the 7.2
module boundary or cannot guarantee exact restored identities.

### Recommended direction

Before proposing this path upstream, ask the RDMA maintainers which core-owned
fixed-handle abstraction they would accept. Prefer declarative fixed-handle
`NEW` semantics if it can support the required restore ordering and error
model. If that framework change is too large for the initial series, use one
narrow callback-based transaction helper as an interim boundary and keep the
raw begin/commit/abort functions out of mlx5.

The import location can be reviewed independently. Keeping it in `main.c`
follows the usual module-metadata convention; moving it into `vfmig_uctx.c`
makes its configuration owner clearer. Neither choice reduces the module-level
namespace acknowledgement or eliminates this item.

### Constraints and open decisions

* Source ufile handles, FW UAR indices, and mmap offsets must remain exact.
  Normal allocation order is not a sufficient restore contract.
* The destination VHCA already owns the imported UAR index after
  `LOAD_VHCA_STATE`; restore must not issue a fresh `ALLOC_UAR` command.
* `MLX5_IB_OBJECT_UAR` is driver-private. A generic solution must support a
  vendor initializer without teaching uverbs core mlx5-specific record
  formats.
* Decide whether the UAPI remains batched. A one-object-per-call interface
  fits the existing dispatcher better, while a batch reduces round trips but
  needs explicit atomicity or partial-commit rules.
* A callback-based helper must define who owns partially initialized driver
  state on failure, whether abort receives `hw_obj_valid=true`, and whether a
  separate cleanup callback is required.
* Provider availability must remain aligned with
  `CONFIG_INFINIBAND_USER_ACCESS` for built-in and modular configurations.

### Completion criteria

* RDMA maintainer feedback confirms the chosen uverbs/core boundary is
  suitable for upstream submission.
* Uverbs core, or one explicitly approved driver-facing abstraction, owns
  exact-handle reservation and the matching commit or abort.
* `mlx5_ib` no longer calls the raw begin/commit/abort triplet directly, unless
  maintainers explicitly approve that exception.
* Restore reproduces the source handle, UAR index, mmap offset, and allocation
  type without issuing a new FW UAR allocation.
* Tests cover duplicate handles, occupied handles, duplicate mmap offsets,
  RDMA-cgroup charge failure, driver-initializer failure, commit success, and
  cleanup of partially initialized state, plus ucontext teardown after partial
  batch failure.
* Batch rollback or partial-commit behavior is specified in the UAPI and
  verified by tests.
* Build and modpost validation cover `INFINIBAND_USER_ACCESS` as `y`, `m`, and
  `n`, with compatible built-in and modular `mlx5_ib` configurations. Include
  `MLX5_INFINIBAND=y` with `INFINIBAND_USER_ACCESS=m`, where the conditional
  mlx5 objects are expected to be omitted from the built-in driver.
* Modular validation confirms that `mlx5_ib.ko` loads and unloads cleanly and
  that `modinfo` or `modules.dep` records `ib_uverbs_support.ko` only when the
  namespaced helpers are linked.
* No ordinary allocation-order or userspace handle-patching assumption is
  required for correctness.

### Upgrade references

* `2274d8cb4912` creates `ib_uverbs_support.ko` and the `rdma_core` namespace.
* `d8f4a0da2ac8` adds the original exact-handle allocator and ordinary exports.
* `1a6fe7ff926a` rebases that allocator onto the namespaced 7.2 interface.
* `d82d5b724ad7` is the original dynamic-UAR restore implementation.
* `ad4b49a53e40` adds the namespace import required by the rebased consumer.

## 3. Define and preserve the complete CQ restore state

* **Status:** Open; includes an immediate correctness fix
* **Area:** RDMA CQ query/restore UAPI and mlx5 CQ software shadow state
* **Estimated effort:** 2-4 days for the narrow mlx5 fix and focused tests;
  1-2 weeks for a paired generic query/restore API and upstream review

### Context

The pre-7.2 mlx5 CQ structure retained the generic
`ib_cq_init_attr::flags` value in `mlx5_ib_cq::create_flags`. The original
VFMIG changes used that field symmetrically:

* `4239bcc80c58` returned `mcq->create_flags` from `QUERY_CQ`; and
* `b7e03bf8f6ad` assigned the restored `attr->flags` to
  `cq->create_flags`.

Upstream commit `eebea464f548` removed the four-byte `create_flags` field.
Ordinary mlx5 creation now retains only
`IB_UVERBS_CQ_FLAGS_TIMESTAMP_COMPLETION` as
`MLX5_IB_CQ_PR_TIMESTAMP_COMPLETION` in the existing `private_flags` mask.
`IB_UVERBS_CQ_FLAGS_IGNORE_OVERRUN` is consumed once while building the FW
CQC, where it sets `cqc.oi`, and is not retained in the kernel object.

The automated rebase resolved that API drift in both halves of the migration
path:

* `f81f258e512c` reconstructs the query response from the timestamp bit in
  `mcq->private_flags`; and
* `5147baccee38` recreates that timestamp bit from the restore flags instead
  of assigning the removed field.

This was a semantic build fix rather than a trivial rename. Git could apply a
new reference to `create_flags` even though the upstream base had deleted the
member, but the result would not compile. The replacement follows how the 7.2
mlx5 create path represents the timestamp option, but it also changes the
observable snapshot from the original generic create-flags mask to the subset
that happens to remain cached in software.

### Correctness and contract gaps

The timestamp conversion itself is justified. mlx5 consults
`MLX5_IB_CQ_PR_TIMESTAMP_COMPLETION` later when selecting the timestamp format
for a QP, RQ, or SQ associated with the CQ. A rebuilt CQ therefore needs that
software bit even though its existing FW CQC was adopted.

The treatment of `IGNORE_OVERRUN` is plausible but not yet proven. The normal
create path writes it only to `cqc.oi`, and no later mlx5 software path reads
the generic bit. If `SAVE_VHCA_STATE` and `LOAD_VHCA_STATE` preserve the whole
CQC for the adopted CQN, the hardware overrun behavior should survive without
replaying the flag. Neither `QUERY_CQ` nor `RESTORE_CQ` currently queries or
validates `cqc.oi`, however, and no focused test establishes that firmware
contract. The rebase comment states the conclusion as fact.

There is also an API inconsistency even if firmware behavior is correct:

* mlx5 `QUERY_CQ` reports `IGNORE_OVERRUN` clear for every source CQ;
* the mlx5 UAPI comments still describe `RESP_FLAGS` as the source
  `cq->create_flags`, although that field no longer exists;
* the generic restore UAPI accepts both standard CQ create flags; and
* mlx5 restore accepts an `IGNORE_OVERRUN` input but neither applies it nor
  verifies that it matches the inherited `cqc.oi` value.

The local variable and UAPI attribute should continue to be called `flags` if
the contract remains the generic `enum ib_uverbs_ex_create_cq_flags` bitmask.
A timestamp boolean would expose an incidental 7.2 implementation detail,
lose extensibility, and make query asymmetric with `UVERBS_ATTR_RESTORE_CQ_FLAGS`.
Internally, a private bit is already the boolean-like representation. If the
intended contract is only "software state that mlx5 must re-latch," the field
could instead be called `restore_flags`, but all UAPI documentation would need
to stop claiming that it contains the original create flags.

The audit also found mlx5-private CQ state outside the generic flags:

* `MLX5_IB_CQ_PR_FLAGS_REAL_TIME_TS` is derived from
  `MLX5_IB_CREATE_CQ_FLAGS_REAL_TIME_TS` and is later consulted while choosing
  timestamp formats for newly created QPs, RQs, and SQs. Restore currently
  clears it.
* `MLX5_IB_CQ_PR_FLAGS_CQE_128_PAD` is derived from
  `MLX5_IB_CREATE_CQ_FLAGS_CQE_128B_PAD` and is consulted during CQ resize.
  Restore currently clears it, so a post-restore resize can encode the CQE
  stride incorrectly.
* CQE compression enablement and mini-CQE format live in the FW CQC rather
  than in `private_flags`. Existing hardware behavior may survive LOAD, but
  this must be validated and any post-restore operation that needs a software
  copy must be identified.

These mlx5-private omissions were already present in the original query and
restore pair. The rebase specifically introduced the loss of the generic
`IGNORE_OVERRUN` bit by removing the old `create_flags` source of truth, while
the comparison exposed the broader pre-existing restore-state gap.

Not every raw create input must be replayed. For example, a flag that only
selects how an already-resolved UAR is supplied is not necessarily persistent
CQ state. The API needs to capture normalized semantics rather than copying
the mlx5 create UHW or the internal `private_flags` representation verbatim.

### Immediate correctness defect found during the audit

Both `b7e03bf8f6ad` and `5147baccee38` assign
`cqe_sz_to_mlx_sz(req.cqe_size, 0)` to `cq->mcq.cqe_sz`. That helper returns a
FW CQC encoding, not a byte count. With padding disabled as it is here, the
result is zero or one. `mlx5_core_cq::cqe_sz` must contain 64 or 128: the
normal create path assigns the byte size, kernel CQ handling compares it with
64 to locate the CQE64 half, and resize copies that many bytes.

Restore should assign `cq->mcq.cqe_sz = req.cqe_size`. The conversion helper
belongs only at a CQC field assignment. With the current value, a restored
64-byte CQ is handled by kernel CQ paths as though its CQE64 starts 64 bytes
into each entry, and copy paths can observe a zero- or one-byte size. User CQs
are normally polled directly by userspace, so this need not break every common
traffic path immediately, but it violates the kernel object invariant and is
not upgrade debt to defer.

The same restore path also pins the wrong CQE-ring length. Source creation
allocates `entries = roundup_pow_of_two(requested_cqe + 1)`, pins
`entries * cqe_size`, and stores `ibcq->cqe = entries - 1`. `QUERY_CQ` emits
that ring-size-minus-one value, but restore currently pins
`attr->cqe * req.cqe_size`. It must use `(attr->cqe + 1) * req.cqe_size` with
an explicit overflow check. Page rounding can hide the missing final entry in
some layouts, but at a page boundary it can change the pinned and rebound page
set.

### Remediation options

1. **Shadow both generic flags in the existing private mask.** Add an
   `MLX5_IB_CQ_PR_IGNORE_OVERRUN` bit, latch it on normal create and restore,
   and reconstruct both standard flags in `QUERY_CQ`. The current `u16` has
   room, so this does not undo the structure-size saving from `eebea464f548`.
   A shared helper should own translation in both directions so query and
   restore cannot diverge again.
2. **Read authoritative FW state during query and restore validation.** Use
   `mlx5_core_query_cq()` to derive `IGNORE_OVERRUN` from `cqc.oi` and inspect
   the resolved CQE stride and compression fields. Query the adopted CQC after
   LOAD and reject metadata that disagrees with FW. This avoids caching a
   hardware-only bit, but requires proving that `QUERY_CQ` is permitted and
   reliable at the selected migration stop point.
3. **Add versioned mlx5 CQ restore metadata.** Extend
   `mlx5_ib_restore_cq_req`, or add a separate response, with a stable
   mlx5-specific semantic mask for at least real-time timestamps and 128-byte
   padding. Decide explicitly whether compression metadata is carried or only
   validated against CQC. Do not expose `mlx5_ib_cq_pr_flags` directly; it is
   an internal representation, not a durable UAPI.
4. **Provide a paired generic CQ snapshot/restore abstraction.** Let RDMA core
   retain the standard CQ create flags in `struct ib_cq`, or add a driver
   callback through which a generic query method obtains normalized
   `ib_cq_init_attr` state. This best matches the generic `RESTORE_CQ` API and
   avoids each provider inventing a different dump-side contract, but it has
   cross-driver and object-size impact.
5. **Narrow and document the current contract.** Define mlx5 `RESP_FLAGS` as
   only the flags required to rebuild kernel software state, document that
   other behavior is inherited from FW, and reject or gate post-restore
   operations whose shadow state is absent. This is the smallest interface,
   but it abandons exact create-attribute round-tripping and is less likely to
   be acceptable as the generic upstream model.

Reintroducing the old four-byte `create_flags` member would be simple, but it
directly reverses the 7.2 memory-layout optimization and still does not cover
mlx5-private state. A new boolean in the public UAPI has the same incompleteness
without the extensibility of a mask.

### Recommended direction

Fix `mcq.cqe_sz` first. For the narrow mlx5 change, retain normalized generic
and provider-specific masks, add an `IGNORE_OVERRUN` shadow bit without growing
the CQ structure, and centralize create/query/restore translation in one
helper. Add stable mlx5 restore bits for the software-visible real-time
timestamp and padding properties.

Use `mlx5_core_query_cq()` in focused validation to prove that LOAD preserves
`oi`, CQE stride, and compression state. Whether production `QUERY_CQ` should
query FW or use the cached shadow can then be decided from command-availability
and failure-semantics results. For upstream, present the standard field as an
extensible flags mask and ask whether its dump-side source belongs in RDMA
core or in a driver callback.

### Completion criteria

* `mcq.cqe_sz` is restored as the 64- or 128-byte software value and CQ polling
  is verified with both entry sizes.
* The restored CQE umem covers `(cqe + 1) * cqe_size` bytes, with overflow and
  page-boundary tests for both CQE sizes.
* `QUERY_CQ` returns an explicitly defined value for all four combinations of
  the two standard flags: zero, timestamp, ignore-overrun, and both.
* Restore either applies every reported generic flag or verifies that the
  inherited FW state already implements it; a caller-supplied mismatch cannot
  silently succeed.
* A CQ can be checkpointed, restored, and checkpointed again without losing
  normalized flag state.
* Pre-SAVE and post-LOAD CQC queries demonstrate whether `oi`, CQE stride,
  compression enablement, and mini-CQE format are preserved.
* A new QP, RQ, or SQ created against a restored timestamp or real-time
  timestamp CQ selects the same timestamp format as before migration.
* A restored padded 128-byte CQ either resizes correctly or resize is rejected
  until its software state can be reconstructed.
* Tests exercise CQ overrun behavior with `IGNORE_OVERRUN` both set and clear.
* UAPI comments describe normalized source state that the implementation
  actually emits; no comment refers to the removed `cq->create_flags` field.
* Unknown future generic and mlx5-specific bits are rejected without exposing
  internal enum values as ABI.
